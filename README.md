# NetSentinel

NetSentinel is a browser-based network operations dashboard and network fault-detection simulator. It provides an interactive topology map, simulated device health metrics, incident detection and management, performance charts, and fault-injection controls.

The project is designed as a self-contained demonstration and learning tool. It runs entirely in the browser and does not connect to real network equipment, collect production traffic, or require an API server.

## What the project does

NetSentinel models a small computer network containing:

- A core gateway
- A distribution switch
- A perimeter firewall
- A wireless access point
- Application and database servers
- Workstations

The application lets you:

- Monitor device availability and health
- Explore and rearrange an interactive network topology
- Create links between devices
- Inspect latency, CPU usage, packet loss, and traffic
- Inject device failures, CPU saturation, and packet loss
- Detect and review network incidents
- Acknowledge and resolve incidents
- View historical-looking traffic and latency charts
- Add simulated devices
- Export the current simulation state as JSON
- Pause and resume the local simulation engine
- Reset the browser state to the original demo network

## Important limitation

This is an educational browser simulator. It does **not** perform:

- SNMP polling
- ICMP or TCP health checks
- Packet capture
- Real infrastructure monitoring
- Network configuration changes
- Authentication or server-side data storage

The metrics and incidents are generated locally for demonstration purposes.

## Application guide

### Overview

The Overview page provides a high-level view of the simulated network:

- Devices online
- Overall network health
- Average latency
- Active incidents
- A compact topology map
- Traffic and latency charts
- Recent incidents
- Device health details

The incident count and health indicators update when the simulation state changes.

### Topology

The Topology page displays devices as nodes and network connections as edges.

You can:

- Drag nodes to reposition them
- Zoom and pan around the map
- Select a device to inspect its details
- Drag from one device handle to another to create a connection
- View link bandwidth labels
- Use the minimap and map controls
- Search devices by name, address, or device type

New devices added with **Add device** are stored in the application state and appear in the topology.

### Incidents

The incident page lists alerts generated by the local detection engine. Incidents have:

- A title
- Severity
- Related device
- Detection time
- Description
- Lifecycle status

Supported statuses are:

- `Open`
- `Acknowledged`
- `Resolved`

Incidents can be acknowledged or resolved from the interface.

### Analytics

The Analytics page presents broader performance information, including:

- Traffic and latency charts
- Availability information
- Device and network summaries
- Explanations of the fault-detection rules

The chart stream is illustrative. It produces new local samples while the simulation engine is running.

### Simulation controls

The simulation engine can be paused or resumed from the sidebar. When running, the application periodically adds simulated traffic and latency samples.

The **Simulate fault** menu provides three scenarios:

1. **Device failure** — toggles a device offline or back online.
2. **CPU saturation** — raises a device's CPU usage to a warning-level value.
3. **Packet loss** — raises packet loss above the warning threshold or clears it.

The affected device, topology reachability, health summaries, charts, and incidents update after a fault is injected.

### Export and reset

**Export** downloads the current simulation as `netsentinel-report.json`. The export includes:

- Export timestamp
- Devices
- Links
- Incidents

**Reset demo** restores the original devices, links, incident list, and running state.

## How the simulation works

### Device and link model

Devices are represented with:

- `id`
- `name`
- `kind`
- IP address
- Health status
- CPU usage
- Latency
- Packet loss
- Traffic level

Links are undirected connections between device IDs with a bandwidth value in Mbps.

The initial network data is defined in [src/engine.ts](./src/engine.ts).

### Reachability

Reachability is calculated using breadth-first search:

1. The core gateway, `gw-01`, is used as the starting point.
2. Offline devices are excluded.
3. Links connected to offline devices are excluded.
4. The graph is traversed through active links.
5. A device is reachable when its ID is found during traversal.

Devices that are online but cannot reach the gateway generate a critical path incident.

### Fault detection thresholds

The detection engine evaluates every device and creates incidents for:

| Condition | Threshold | Severity |
| --- | --- | --- |
| Device offline | Health is `offline` | Critical |
| High CPU | CPU is at least 85% | Warning |
| Critical CPU | CPU is at least 95% | Critical |
| Packet loss | Packet loss is at least 3% | Warning |
| High latency | Latency is at least 100 ms | Warning |
| Missing route | Online device cannot reach gateway | Critical |

Incident IDs are derived from the device and condition. This prevents the same currently detected incident from being inserted repeatedly on every render.

### State management

The main application state is managed by Zustand. It contains:

- Devices
- Links
- Incidents
- Simulation running state
- Device update actions
- Link creation actions
- Device creation actions
- Acknowledge and resolve actions
- Reset action

The Zustand persist middleware stores the state in browser `localStorage` under:

```text
netsentinel-state
```

As a result, changes remain after refreshing the browser. Use **Reset demo** to return to the seed data.

### Generated metrics

The initial chart contains simulated traffic and latency points. While the engine is running, a new sample is appended every four seconds and the oldest sample is removed.

These values are generated with local random and trigonometric functions. They are not measurements from a real network.

## Deployment to GitHub Pages

The repository includes a GitHub Actions workflow at [.github/workflows/deploy.yml](./.github/workflows/deploy.yml).

The workflow:

1. Runs when changes are pushed to `main`.
2. Can also be started manually with `workflow_dispatch`.
3. Uses Node.js 20.
4. Installs dependencies with `npm ci`.
5. Runs `npm run build`.
6. Uploads `dist/` as a Pages artifact.
7. Deploys the artifact to GitHub Pages.

To enable deployment in GitHub:

1. Open the repository's **Settings**.
2. Select **Pages**.
3. Set the build and deployment source to **GitHub Actions**.
4. Push changes to `main` or run the workflow manually.

The Vite configuration uses `base: './'`, allowing the generated assets to work when served from a GitHub Pages project path.

## Troubleshooting

### `npm` or `node` is not recognized

Install Node.js 20 or newer, restart the terminal, and verify:

```bash
node --version
npm --version
```

### Dependencies appear incomplete

Remove the local dependency directory and reinstall from the lockfile:

```bash
npm ci
```

Do not commit `node_modules/`.

### The browser shows old data

NetSentinel intentionally persists state in `localStorage`. Use **Reset demo**, or clear the `netsentinel-state` local-storage entry for the site in browser developer tools.

### The production build fails

Run the build again and inspect the first TypeScript error:

```bash
npm run build
```

The build performs strict TypeScript checking before Vite creates the production assets.
